## Goal

Redesign the Kira Learn homepage from a simple article grid into a futuristic public study console for AI agents, orchestration, systems design, and architecture patterns.

The site should still work as a public blog, but the first impression should be: this is a refined spatial learning atlas where articles are connected to maps, learning paths, open questions, and evolving system diagrams.

## Audience

- Primary: the site owner using Kira Learn as a personal AI and systems-design learning cockpit.
- Secondary: public readers who want a guided way into agentic systems, tools for thought, orchestration, and architecture notes.

## First Viewport

The first viewport should lead with the current map, not a generic publication intro. The composition should be visual-first and less text-heavy than a dashboard: a concise left intro, a large central/right map, and one restrained current-question rail.

Required elements:

- Top navigation with `Kira Learn`, `Maps`, `Paths`, `Notes`, `Sharp view`, and a compact search/control surface.
- Main headline: `Mapping the agentic systems stack`.
- Supporting copy: `A public study console for AI agents, orchestration, systems design, and the architecture patterns behind the tools.`
- Primary action: `Open current map`.
- Secondary action: `Read latest note`.
- Large system-map visualization with connected nodes. This is the visual anchor of the page and should occupy more attention than the surrounding text:
  - `Agent loops`
  - `Orchestration`
  - `Tool protocols`
  - `Memory`
  - `Evaluation`
  - `Product systems`
- A detail panel titled `Current question` containing: `When does agent orchestration become product architecture?`
- A small latest-note area under the hero copy, using `Orchestration boundary playbook v0.2`.

The map should feel like a live research interface and a systems observatory, but it can be implemented as semantic HTML/CSS/SVG in this static site. It must not be shipped as a screenshot.

## Homepage Sections

### Current Mapping

Purpose: show what the study console is actively investigating.

Content model:

- Two open questions.
- One latest artifact.
- Link to view all artifacts.

Initial copy:

- `How do we design durable agent loops?`
- `What is the minimal viable orchestration layer?`
- `Orchestration boundary playbook v0.2`

### Learning Paths

Purpose: route visitors into guided study sequences rather than forcing them to browse chronologically.

Initial paths:

- `Agentic architecture`
- `Systems design`
- `Tools for thought`

Each path should include a short descriptor, progress-style visual indicator, count, estimated reading time, and a link affordance.

### Article Clusters

Purpose: preserve article discovery while making the archive feel organized by mental model.

Initial cluster columns:

- `Architecture`
- `Systems`
- `Tools`
- `Product`

Each cluster should list a small set of topic rows with counts. Rows should be dense, restrained, and scannable. Avoid a repetitive marketing-card grid.

### Evolving Diagrams

Purpose: make systems diagrams a first-class artifact alongside articles.

Content model:

- One prominent diagram preview.
- A related notes list.
- Link to all diagrams or related notes.

The diagram preview can be implemented with inline SVG and code-native labels.

## Visual System

Use the second generated concept as the styling source.

Design characteristics:

- Near-black graphite background.
- Cyan as the primary luminous accent.
- Restrained indigo as a secondary accent.
- Cool gray text hierarchy.
- Fine borders and grid lines.
- Compact 6-8px radii.
- Precise technical typography using the existing Inter import.
- Spacious, visual-first atlas composition.
- Dense where useful below the hero, but never visually overloaded.
- No decorative gradient orbs, bokeh, oversized marketing panels, or generic hero wallpaper.

The page should feel futuristic, calm, and useful: a systems architect's learning observatory rather than a cyberpunk poster or SaaS admin dashboard.

## Implementation Constraints

The repo is a static site generated by `build-index.js` through `lib/render-index.js`.

Implementation should:

- Update `lib/render-index.js` as the source template.
- Run `npm run build` so `index.html` is regenerated.
- Keep article links generated from the existing article metadata.
- Preserve the `/sharp` route link.
- Keep the homepage fully static, with no client framework required.
- Use code-native HTML/CSS/SVG for maps, diagrams, controls, labels, and article lists.
- Add only small helper functions if they clarify clustering or latest-article selection.

## Interaction

Required interactions for the first implementation:

- Article cards and cluster/topic rows link to existing articles where possible.
- `Read latest note` links to the newest article.
- `Sharp view` links to `/sharp`.
- Hover states clarify clickable items.
- Search/control surface may be visual-only for this pass unless a simple no-JS link target already exists.

## Responsive Behavior

Desktop:

- Hero uses an asymmetric atlas layout: copy/actions/latest note on the left, live system map across the center/right, current-question rail on the far right when space allows.
- Lower sections use a refined research-desk layout matching the second concept, with clear dividers and restrained panels.

Tablet:

- Hero can stack while keeping the map immediately after the headline/actions.
- Dashboard sections should become two-column where space permits.

Mobile:

- Navigation compresses without horizontal overflow.
- Hero headline remains readable.
- System map scales within its container.
- Lower panels stack in a logical order: Current Mapping, Learning Paths, Article Clusters, Evolving Diagrams.

## Testing

Run:

- `npm test`
- `npm run build`

Visual verification:

- Open the generated `index.html` in the browser.
- Compare against the approved concept image.
- Check desktop and mobile widths.
- Verify no text overlaps, map labels remain readable, and generated article links work.

## Out of Scope

- Real search.
- Persistent learning progress.
- A separate maps database.
- New article taxonomy files.
- Client-side routing or a JavaScript app shell.
- Redesigning individual article pages unless a later pass requests it.
